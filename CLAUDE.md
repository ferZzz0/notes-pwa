## Project Overview

A notes app as an installable, offline-capable PWA: React 19 + TypeScript + Vite 8. The PWA layer (Workbox service worker + web manifest) is generated by `vite-plugin-pwa`. Hosted on **GitHub Pages**: every push to `main` of `github.com/ferZzz0/notes-pwa` runs [.github/workflows/pages.yml](.github/workflows/pages.yml) (`npm ci`, `npm run check`, `npm run build`, `dist/index.html` copied to `404.html`, deploy via `actions/deploy-pages`). Production URL: https://notes-polik.sokolovpk.ru — custom domain set in the repo's Settings → Pages; the DNS zone stays at Cloudflare with a CNAME `notes-polik` → `ferzzz0.github.io`, **DNS only (grey cloud)** — never proxied. UI text and code comments are in Russian.

**Why not Cloudflare (moved 2026-10-25, user's decision).** It used to be Cloudflare Workers Static Assets (like the sibling `C:\myGit\zuma-pwa`; [wrangler.jsonc](wrangler.jsonc) is left from that and can be deleted once the Worker is disconnected). Russian ISPs stall connections to Cloudflare's `188.114.96.x` / `188.114.97.x` after ~24 KB: the HTML loads, the JS bundle hangs, the page stays blank (and installed apps can't download updates). `104.21.46.231` / `172.67.143.35` worked, but which pair a client gets is a DNS lottery (on 2026-10-25 the system resolver and Google `8.8.8.8` returned the bad pair, Yandex `77.88.8.8` and `1.1.1.1` the good one; `*.workers.dev` always bad), and it isn't fixable on the free plan. GitHub Pages (`185.199.108–111.153`) was tested from the same Russian network: a 309 KB file in 0.6 s, no stall. Don't move the site back behind a Cloudflare proxy.

To verify a deploy: `curl -s https://notes-polik.sokolovpk.ru/version.json` shows the build time (also visible in the app's settings); `curl -sI` should show `server: GitHub.com`. The Pages deploy takes ~1–2 minutes after a push (Actions tab).

## Workflow: always deploy

The user reviews every change on their phone (iPhone) against the deployed site, not locally. So after each finished change, without asking: run `npm run check` and `npm run build`, and if both pass, commit and push to `main` — GitHub Actions deploys it to GitHub Pages. Never push a failing build. Then confirm the new version is live on https://notes-polik.sokolovpk.ru. Remind the user that the installed app picks it up via the «Доступна новая версия» → «Обновить» banner.

## UI

- **The product (user's decisions, 2026-10-25):** an open school notebook. The sheet ALWAYS fills the whole screen — status-bar/notch/home-indicator strips included; nothing but paper is ever visible, there is no desk and no «К началу листа» button (both removed at the user's request). A sheet is exactly ONE SCREEN at first (locked: it can't be panned or zoomed out, only zoomed in); when text comes near an edge, another whole screen of paper opens in that direction (down; outward to the side; never across the spine of a single page, never above the top). Portrait shows one page, landscape the spread; text can be written anywhere on the paper (double-tap), and a text is fully editable while and after writing it — a tap selects it (menu, no keyboard), another tap types; move with a finger, rotate/resize with two fingers (no handle buttons), colour from a colour wheel, font and letter effect from drop-down lists, marker presets on a written text, delete with confirmation; own photos (PNG too) and ready-made stickers to write on, both fully adjustable; pages turn by curling up from the bottom outer corner. Plain paper — NO grid (the user asked to remove it: after a swipe the re-rasterized grid visibly redrew) and NO fold shadow along the spine (removed at the user's request; only the thin spine line remains in the spread). There is a MAIN MENU (user's request, 2026-10-25) with several named diaries and a calendar — a date opens one sheet of notes for that day. New/empty sheets show ONLY the page number (no help text, no faint date — user's request). The bottom row (centre) is: undo, redo, main menu, «+», gear. Pages turn by SWIPING the sheet sideways — there are no arrow buttons (user's request, 2026-10-25; ←/→ keys on a computer). The gear opens settings, which for now hold debug tools only: this build's time vs the server's, «Обновить» and «Стереть все данные». The manifest has no `orientation`.

- **World coordinates:** `y = 0` is the top of the writing area (at home it sits at the top of the safe area; the paper continues above it under the status bar), the spine is `x = 0`; left page `x < 0`, right page `x ≥ 0`. Text sizes are in world px (Caveat 40px / 52px lines; other fonts in TextBlock.css).
- **[src/components/Canvas.tsx](src/components/Canvas.tsx)** — the pan/zoom engine, hand-written (no library) for full control over how gestures coexist with text input. Camera `{x, y, scale}` (screen = world·scale + x/y) is written straight to `.canvas-world`'s `transform` (no React re-render per frame). Generic: `home` (start view: `width` of world fills the safe-area width (scale ≥ `minScale`), world point `(x, y)` at the top of the safe area and at the centre / left / right edge per `align`), the sheet bounds (`content` rect, `fixed` edges, `bounded`, `extraBottom` — below), `locked`, `background` (screen-space layer under the world), `onFrame(cam, size)`/`onTap`/`onDoubleTap` callbacks, `onLongPress(world, screen, touch)` (a touch/pen finger held `LONG_PRESS_MS` = 500 ms within the tap slop, not on an interactive element or a grabbed item; its release is then NOT a tap, and its `touchend` calls `onLongPressEnd(true)` (user activation — the clipboard may be read there) and is `preventDefault`ed; a `touchcancel` instead calls `onLongPressEnd(false)`; to keep iOS from cancelling long touches, `touchstart` is `preventDefault`ed on every canvas target except editable ones (the text being typed keeps native caret/selection/loupe); `nativeTouch(target, x, y)` (Notebook) gives touches to the browser entirely — no pan, grab, tap or long press, no `preventDefault` — when they land on the text being typed, or within `HANDLE_PAD` = 32 px of it while something is selected (iOS selection handles stick out of the text; the canvas used to pan instead of dragging them — user report, 2026-10-26); so a text can't be dragged while it's being typed in; a mouse right-click calls `onLongPress(…, false)` via `contextmenu`, whose default menu is always suppressed — Android also sends `contextmenu` for a touch long press, which the timer already handled), `onSwipe(dir)` (a one-finger flick: ≥ `SWIPE_PX` = 50 px, under `SWIPE_MS` = 700 ms, `SWIPE_RATIO` 1.5× more sideways than vertical, while the camera moved less than `SWIPE_SLIP` = 25% of the finger's path — i.e. the sheet was at home or already against its edge, hard clamping stopped it; finger left = `'next'`; passes where the finger started and the canvas width; no inertia after it; never for pinches or grabbed items) and `grab` (a gesture whose first finger lands on something grabbable goes to it instead of the camera — `Grab` begin/move/end with 1–2 screen points) (all kept in a ref, so the once-subscribed listeners see fresh props), and a ref handle `goHome(home?, duration?)` (Promise; optional explicit target; resolves at once when the camera is already there), `visibleRect()`, `panBy()`.
  - **Sheet bounds** (`computeBounds`): the base is exactly the WHOLE screen at the `home` camera (inset strips included — home scale/position use the safe area, the paper doesn't). For every edge not in `fixed`, while `content` is within `EDGE_ZONE` (20%) of a screen from it, the edge moves out by a WHOLE screen (`steps()`), so sheets grow in screen-sized chunks. **The sheet keeps the screen's proportions** (user, 2026-10-26: «расширили по горизонтали — должен расшириться и по вертикали, и наоборот»): after the per-edge growth, the screens across and down are equalized to `n = max` of the two — extra width goes to the free side(s) (a spread: half to each, spine stays centred; one page: outward), extra height downward. So any grown sheet can be zoomed out to exactly 1/n — the short side no longer blocks zooming out. `extraBottom` (screen px) temporarily lengthens the bottom so a line can be lifted above the keyboard: Notebook passes the open keyboard's height from `visualViewport` (+ the toolbar's while something is selected), or `KEYBOARD_GUESS` (60% of the screen) for `TYPING_RESERVE_MS` = 1 s after `focusText()` (until the keyboard has opened — or it's a computer and none will), and NOTHING while only a toolbar is open without the keyboard (user: the sheet must not be movable down then). Clamping is hard: the sheet must cover the whole screen, min scale = "sheet covers the screen" (so an unextended sheet can't be zoomed out at all), max 2.5. `bounded={false}` lifts all of it (Notebook does that during transitions). When the bounds props change, `reclamp()` animates the camera back inside. Insets are measured in `measure()` (on resize and `goHome`), not per frame.
  - Gestures: one pointer drag = pan (after an 8px slop, so taps stay taps) with inertia on release (velocity of the last 100 ms, capped); two pointers = pinch around their midpoint + pan; wheel = pan, Ctrl/⌘+wheel (and Chrome's trackpad pinch) = zoom; Safari's Mac trackpad pinch comes only as `gesture*` events (ignored while touch pointers are active — on iOS they duplicate pointer events, we only `preventDefault` them). A single tap on non-interactive space blurs the focused field (closes the keyboard); a double tap there calls `onDoubleTap(worldPoint)`.
  - **After any resize/rotation the view is ALWAYS the standard `home` view** — the start of the sheet at the standard size, however it was zoomed and however far the sheet has grown (user's request, 2026-10-25; it was "fully zoomed out" before, which made a sheet grown sideways smaller than standard); applied on every ResizeObserver step (iPhone rotation resizes in several steps) and via the handle's `showHome()`. The very first layout is `home` too (in `useLayoutEffect`, no flash).
  - `touch-action: none` on `.canvas` AND all descendants — otherwise a scrollable/editable child (a text) claims the touch and the browser fires `pointercancel` mid-pan.
  - Pointer capture is taken only once a gesture becomes a pan/pinch, so a plain tap still focuses a text. Mouse presses on editable elements are ignored by the canvas (text selection works). Elements with `[data-no-pan]` are ignored entirely.
  - **Performance — the fix for the user's "lags with two fingers" (2026-10-25).** The world is ALWAYS its own compositor layer (`will-change: transform`), so pan/pinch only move/scale a ready bitmap. Camera writes are batched to one `transform` write per animation frame (pinch delivers a move per finger). After the camera settles (200 ms) and only if the scale changed, `settle()` drops/restores `will-change` once so text re-renders crisply. Chromium trace of a 120-move pinch: Paint 346 → 4, RasterTask 2083 → 20 (the old version changed a `--zoom` CSS variable every pinch frame, repainting the whole grid, and toggled the layer at every pause). Don't reintroduce per-frame style changes on the world or `will-change` toggling during gestures; keep big blurred shadows out of the world.
  - Safe-area insets are read from a hidden probe element (`env()` exists only in CSS).

While a text is focused Canvas has `inertia={false}`, so the sheet stops with the finger. When the APP moves the camera while typing (keepVisible's `panBy`, reclamp), the selection can't be removed (typing continues), so `followCaret` re-sets it on EVERY frame — the caret follows the text (user: «курсор иногда плывёт»); never during IME composition (`data-composing` on the text, set by TextBlock).   - **Rich text (user's request, 2026-10-25: a style applies to the SELECTED part of a text; with nothing selected — to the whole text, as before).** [src/richText.ts](src/richText.ts): a block may have `runs: [{ t, color?, font?, effect?, marker? }]` — together exactly `text`, a run's style overrides the block's; stored only when some run is styled (`compactRuns`), otherwise `text` alone. The piece the toolbar styles (`captured`) follows the text's selection all the time (`selectionchange` → `takeRange`), EXCEPT for changes within `TOOLBAR_GRACE_MS` = 700 ms of touching the toolbar (`onCapture` on its `pointerdown`/`pointerup` capture): on iPhone the toolbar tap itself can drop the selection — then the list item applied to the whole text / nothing seemed selected (user report, 2026-10-26). ## PWA notes

- Configured in [vite.config.ts](vite.config.ts): `generateSW` mode, `registerType: 'prompt'`. The precache list is built from the hashed output, so there is NO manual cache-version bump — every build that changes files ships a new `sw.js`.
- [src/components/UpdatePrompt.tsx](src/components/UpdatePrompt.tsx) registers the SW via `useRegisterSW` (`virtual:pwa-register/react`, typed through [src/vite-env.d.ts](src/vite-env.d.ts)), shows the "offline ready" / "new version" banner (`z-index: 100` — ALWAYS above everything, the user asked for that), and calls `registration.update()` hourly AND whenever the page becomes visible again (`visibilitychange`) or the network comes back (`online`). The visibility check matters on iPhone: an installed app reopened from the home screen usually resumes from the background instead of relaunching, so the browser never checks for an update and iOS freezes the hourly timer — the user once saw no banner at all after a deploy. Updates never auto-reload — the user taps «Обновить», so an in-progress note is never lost to a reload; if the page isn't controlled by a SW yet (very first launch), the new SW has already activated without waiting, so «Обновить» just reloads. Why the banner may not show (user report, 2026-10-25): it appears only when the new SW finished installing while the app is open — the install can stall on throttled Cloudflare IPs (see above), and after a full close/reopen a downloaded version activates by itself with no banner. The settings' «Обновить» and the build/server times are the debugging aid for this.
- Manifest icons in `vite.config.ts` must match the files `npm run icons` writes to `public/`.
- The Claude desktop browser pane cannot register service workers at all; verify SW behavior in real Edge/Chrome (e.g. headless via playwright-core) against `npm run preview`.
